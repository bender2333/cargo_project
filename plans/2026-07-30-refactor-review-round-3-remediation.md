## 任务 1：修复自动装箱的 capacity-one 后插入违约

### 问题

自动算法会把后放置的 `maxStackLayers=1` 或不可堆叠货物插入已有上层箱下方，形成超过允许层数的支撑链。普通单测和 packing-performance 各有一条稳定失败。

### 根因

放置校验只沿新箱的支撑链向下检查；当新箱成为已有箱体的支撑物时，不会向上复核已有乘员。最终支撑重算只能报告错误，不能撤销非法位置。

### 解决方案

在候选位置提交前，基于加入新箱后的局部支撑图，同时校验新箱向下链和受它影响的已有上层链。所有算法分支共用同一校验。非法候选被拒绝并继续寻找其他位置，不采用事后删除箱体的补救方式。

### 验收标准

- 两条现有 capacity-one RED 保持原断言并转绿。
- 所有自动结果逐箱执行 `violatesStackChain` 均返回 `null`。
- 不越界、不重叠、不超重、ground-only、支撑面积和朝向约束继续通过。
- 俄罗斯 31 托在指定自定义柜型、volume 模式下仍为 `31/31`。
- 业务合同发生变化时先审查逐箱差异，不直接刷新 baseline。

## 任务 2：建立自动和手动共享的 PackingResult 终结流程

### 问题

自动路径会重算最终支撑、层级和拓扑作业顺序；手动路径仍把箱体伪装成落地第 1 层、无支撑，再独立拼装 `PackingResult`。`depthLayer` 还是可选字段且未进入冻结合同。

### 根因

`PackingResult` 由自动和手动两个生产者分别组装，没有一个模块统一维护支撑、层级、作业顺序和诊断不变量。

### 解决方案

建立单一结果终结流程。输入最终坐标、柜体、货物计划和来源诊断，统一派生垂直支撑图、`physicalLayer`、`depthLayer`、支撑拓扑作业顺序、layers、diagnostics 和汇总。自动算法只产生坐标与未装入原因，手动模式只产生草稿坐标与手动校验，两者都必须经过该流程。

### 验收标准

- 合法手动叠箱具有真实 `supportedBy`、`supportType` 和 `physicalLayer`。
- 自动和手动对同一最终坐标产生相同的支撑、层级和作业顺序。
- 每条支撑边满足支撑物先装、上层箱后装。
- 完成结果中的 `depthLayer` 必有，并进入 canonical contract。
- 删除手动伪支撑字段和重复终结逻辑，不保留影子字段或兼容旁路。

## 任务 3：统一合规判定、诊断和保存导出命令

### 问题

当前只禁用了结果面板的主 XLSX 和保存按钮。历史页、回放 XLSX、loading sheet PDF、当前视图和复核导出仍可绕过；自动 error diagnostic 也不阻止保存导出。复核清单会遗漏 diagnostics，手动超重可能生成重复 diagnostic ID。

### 根因

合规被放在局部 UI 状态中，而不是保存和导出命令的业务入口。诊断又由多个来源拼接，没有统一去重和审核投影。

### 解决方案

建立统一合规判定，自动和手动方案共用。任何保存或正式导出命令都必须先检查结果与手动问题；error 阻止命令，warning 按明确规则保留并写入文件。诊断页、复核清单、JSON 和 Excel 使用同一诊断集合和唯一 ID。

### 验收标准

- 自动 stacking error 和手动 boundary、overlap、floating、stacking、overweight error 均阻止所有保存和正式导出入口。
- 历史页和直接调用命令不能绕过守卫，失败必须可见。
- 诊断页、复核清单、JSON 和 Excel 的 error 数量与 ID 一致。
- 同一超重问题只生成一个 `weight-check`。
- warning-only 方案按统一规则处理，不被误判为 error。

## 任务 4：统一手动模式生命周期、货物同步和快捷键作用域

### 问题

进入手动模式的自动结果转换逻辑重复；空草稿同时表示“未初始化”和“用户主动删空”。货物编辑只同步部分属性，尺寸、旋转能力和全局默认层数仍可能陈旧。全局撤销/重做还能在自动模式或其他页面修改隐藏草稿。

### 根因

手动 session 没有显式初始化状态和草稿来源；自动结果转草稿、CargoItem 对账没有单一函数；快捷键没有限制在活动手动工作区。

### 解决方案

显式记录手动草稿的初始化状态和来源，抽出唯一自动转草稿逻辑。货物对账同步尺寸、基础尺寸、`canRotate`、堆叠属性和默认层数，并在变化后重新校验几何。撤销/重做仅在手动工作区且非表单焦点时生效。以“首次进入手动模式继承当前自动方案”为统一合同修正现有 E2E。

### 验收标准

- 首次进入手动模式无损继承坐标、朝向、标签和规则。
- 用户主动删空后切换模式，重新进入仍保持空。
- 编辑货物后 past、present、future 和活动结果没有陈旧几何或规则。
- 非法新几何明确标红并被任务 3 的合规守卫阻止。
- 自动模式、历史页和模板页按 Ctrl/Cmd+Z/Y 不修改手动草稿。
- 当前 8 条冲突 E2E 按统一语义全部转绿。

## 任务 5：实现事务式 Excel 导入和确认前业务预览

### 问题

导入在同批存在错误时仍可能用有效行覆盖当前货物。映射弹窗只显示原始单元格，确认前看不到转换结果和错误统计；缺失或非数字重量会静默成为 0。弹窗还缺少标准 modal 与键盘焦点边界。

### 根因

解析、预览和提交没有独立状态；解析结果直接进入 `cargoImported/onConfirm`。重量解析无法区分真实值与非法回退值。

### 解决方案

采用“解析 → 暂存预览 → 显式确认 → 一次性提交”流程。默认整批拒绝含错误行的导入，确认前不改变 cargo、手动草稿或 session revision；取消后状态不变。预览复用正式解析器，展示标准化字段、毫米尺寸和行级状态。重量必须是大于 0 的有限数。弹窗补齐 dialog、初始焦点、焦点约束、Escape 和焦点恢复。

保持既有模板合同：选择模板只预填、立即提示缺列、必须显式确认；同名已选模板用 PUT，否则 POST；保存失败可见；保留 `combinedColumn || mapping.dimensions` fallback。

### 验收标准

- 含有效行和错误行的工作簿不会在确认前覆盖当前数据。
- 取消导入后 CargoItem、手动草稿和 inputRevision 逐字段不变。
- 预览展示转换后的 L/W/H、重量、数量、标签及成功/错误/警告/厘米换算统计。
- 缺失、非数字、零或负重量均为具体行错误，不进入算法为 0 kg。
- 模板预填、缺列提示、PUT/POST 判定、失败反馈和 legacy fallback 保持有效。
- `test-data/excel` 既有场景及 31 托完整 E2E 通过。

## 任务 6：统一按标签统计和结构化实际朝向导出

### 问题

`labelStats` 仍按 CargoItem 逐行产生，同一业务标签可能重复；显示层再二次去重。混合朝向导出只清空实际尺寸并写备注，无法知道每种朝向的数量。

### 根因

标签聚合和 cargo 明细混用了同一统计结构；导出行模型没有朝向维度，只能压缩并丢失信息。

### 解决方案

`labelStats` 按规范化业务标签聚合，cargo 明细继续按 cargoId 计算，不从聚合统计反查。导出增加结构化 `orientationKey` 和朝向数量，混合朝向固定按“cargo × orientation”拆行；默认导出和自定义模板使用同一合同。

### 验收标准

- 同标签多条 CargoItem 在 `labelStats` 中只出现一次，聚合数量和层级正确。
- cargo 明细仍按 cargoId 正确展示计划、已装和未装数量。
- 混合朝向导出能精确给出每个 orientationKey 的数量与实际尺寸，数量合计等于 placed 数。
- 单一朝向、等边尺寸和无已装箱体均有无歧义输出。
- 2D、3D、明细、loading sheet、历史摘要和导出使用一致标签口径。

## 任务 7：实现带版本的历史方案快照

### 问题

历史记录只保存输入和摘要，恢复时使用当前算法重算；自动方案会随算法版本变化，手动坐标和模式完全丢失。

### 根因

历史合同没有 schema version 和结果快照，旧记录实际是输入模板而不是装柜方案。

### 解决方案

新增版本化快照，保存模式、柜体与货物输入、已放坐标与朝向、支撑层级、作业顺序、未装入、diagnostics、标签统计，以及恢复手动模式所需的完整草稿和初始化来源。新版记录直接验证并恢复快照，不用当前算法替换；旧记录明确标为输入模板，经用户确认后才重算。为大方案设定可审计的大小限制或压缩方案。

### 验收标准

- 自动方案跨算法版本恢复后逐箱坐标、朝向、层级和步骤一致。
- 手动方案恢复后模式、草稿和校验结果与保存时一致。
- 未知版本、损坏或超限快照失败可见，不静默重算。
- 旧记录显示明确降级提示，确认后才按当前算法计算。
- 用户隔离、历史数量上限、删除和旧数据库迁移继续有效。
- 使用真实大方案验证存储与响应大小。

## 任务 8：解决账号与用户管理范围冲突

### 问题

仓库规则写明本期不做账号管理类产品功能，PRD 又要求保留管理员登录审计能力；当前仍暴露完整 Users 页面，文档和实现没有统一结论。

### 根因

基础设施能力、管理员审计和用户 CRUD 产品入口没有明确分层。

### 解决方案

在 `decision.md` 固定范围。推荐保留登录、token、数据隔离和管理员审计基础设施，本期隐藏用户 CRUD 产品入口；如果产品决定继续保留用户管理，则同步修订 PRD 和仓库规则，不能保留冲突。

### 验收标准

- `decision.md` 明确保留能力、隐藏入口和访问角色。
- PRD、仓库规则、导航和权限行为一致。
- 非管理员无法发现或访问管理能力。
- 登录、登出、token 失效、用户隔离和管理员审计回归通过。

## 任务 9：收口前端架构、登录前加载和 benchmark

### 问题

Workbench 仍集中大量状态和命令，区域组件通过 60+ props 回传控制；ContainerScene 仍超过既有拆分目标；App 登录前静态导入 Workbench。benchmark baseline 曾吸收合同与包体变化，当前 initial JS/total 和 3D 首像素仍 RED。

### 根因

此前主要移动 JSX，没有下沉状态所有权和命令；Three.js 初始化与事件生命周期仍集中；登录壳没有隔离重型工作台依赖；baseline 更新缺少可信审批闭环。

### 解决方案

业务任务稳定后分三次独立提交：

1. 将 Results、Visualization、import/export/history 的局部状态和命令下沉到现有 feature controller，不引入全局状态库。
2. 拆分 ContainerScene 的静态 scene setup 和事件作用域，保持单一 scene graph 与现有生命周期。
3. 让未登录首屏按需加载 Workbench/Three.js，并从批准固定点恢复可信 benchmark 基线；合同差异和包体变化逐项审批。

### 验收标准

- `Workbench.tsx` 不超过 1500 行；ResultsPanel 和 VisualizationWorkspace props 各不超过 25 项，不能用无类型大对象规避。
- `ContainerScene.tsx` 达到既有计划的 `≤600` 行目标，且没有监听器、RAF、材质或 renderer 泄漏。
- 未登录初始依赖不包含 Workbench/Three.js；登录后加载失败有可恢复状态。
- 3D 非空画布、视角、resize、标签、拖拽和旋转 E2E 全绿。
- benchmark 合同与已批准业务结果一致；initial HTML/CSS/JS/total 不高于批准基线，total JS 满足 5% 门禁。
- 3D 首像素 median/P95 回到同机 20% 门内；不更新 baseline 掩盖不可解释回退。

## 全局验收

全部任务完成后统一执行：

```bash
npm run lint
npm test
npm run build
npm run test:e2e
npm run benchmark
```

最终交付必须满足：

- 所有命令退出码为 0，零 skipped，不再使用“已知 RED 下通过”的表述。
- 31 托真实 Excel 完整 UI 流程保持 `31/31`。
- 自动和手动方案存在 error 时均不能保存或正式导出。
- 历史恢复、导入确认、标签统计、朝向导出和中英文流程有对应 E2E。
- 每个任务独立提交并更新 `CHANGELOG.md`；决策写入 `decision.md`。
- 本地全绿后按项目流程部署并运行远程 E2E，结果写入 `CHANGELOG.md`。

## 非目标

- 不引入全局状态库、规则引擎或抽象工厂。
- 不重写后端；历史快照只做必要 schema 和接口扩展。
- 不新增在线协作、复杂权限或许可证能力。
- 不降低 benchmark 样本、阈值或合同保护。
- 不保留自动/手动双终结流程、影子支撑图或废弃字段兼容层。
